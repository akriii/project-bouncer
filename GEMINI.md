# Project Bouncer: AI Context & Blueprint

## The Mission
**Bouncer** is a B2B SaaS platform ("Waiting Room as a Service") designed to protect high-demand drops (concert tickets, limited-edition sneakers, etc.) from scalper bots and server crashes. It acts as a digital dam, absorbing massive traffic spikes, mathematically neutralizing time-based scalping, and queuing real humans fairly.

## Tech Stack
*   **Backend (Completed):** Python, FastAPI, Redis (for high-speed state/queues), WebSockets, Docker.
*   **Frontend (Upcoming):** Next.js (App Router), React, Tailwind CSS.
*   **Database/Auth (Upcoming):** Supabase (PostgreSQL) for permanent storage and Google OAuth.
*   **Hosting (Upcoming):** Vercel (Frontend), Render (Backend container + Redis).

## The Core Engine (The 3 Tiers)
Bouncer routes traffic dynamically based on the client's paid subscription tier.

1.  **Tier 1: High-Concurrency Core (The Digital Dam)**
    *   Standard FIFO (First-In, First-Out) queue.
    *   Maintains real-time connection with users via WebSockets.
    *   Pushes users to the secure checkout page when it is their turn.
2.  **Tier 2: Anti-Bot WAF (The Shield)**
    *   Sliding-window rate limiting.
    *   Headless browser detection and bot signature blocking.
    *   Deflects automated scraping scripts before they hit the queue.
3.  **Tier 3: Intent & Lottery (The Scalper Killer)**
    *   **Cryptographic Intent:** Requires a signed JWT (`pre_cart_intent`) generated by the client's secure backend to prove the request is legitimate.
    *   **Holding Pool:** Users arriving before the drop are placed in an unordered Redis Set (`lottery_pool`) rather than a list.
    *   **The Grand Shuffle:** When the admin triggers the "Go Live" API, Bouncer scrambles the holding pool and pushes everyone into the active queue simultaneously, neutralizing the advantage of time-based bot camping.

## Multi-Tenant SaaS Architecture
Bouncer operates as a true multi-tenant platform.
*   **`client_id` (Public):** Hardcoded in the client's React frontend. Used to identify the client (e.g., `org_flash_tix_991`).
*   **`secret_key` (Private):** Hidden on the client's backend. Used to cryptographically sign Intent Tokens.
*   **The Routing Logic:** When traffic hits `/join`, Bouncer reads the `client_id`, fetches their active subscription config from Redis in microseconds, and applies Tier 2 and Tier 3 security checks *only* if the client is paying for them.
